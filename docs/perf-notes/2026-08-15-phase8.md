# Phase 8 notes — consensus off the hot path, measured

The claim clustering rests on is that the data plane never waits for the
control plane. Phase 8 adds Raft, so the claim needed testing rather than
repeating.

## Leader death under load

A 3-node cluster of real binaries on loopback, continuous traffic against
a *follower*, `kill -9` on the leader mid-flight:

| | |
|---|---|
| Requests issued during the kill | 150 |
| Non-200 responses | **0** |
| Shares after failover | rescaled 3 → 2 automatically |
| Config writes | resumed on the surviving majority |

The data plane reads a local snapshot, so an election is invisible to it.

## Minority partition

Two of three nodes killed, leaving one node in a minority:

- 30 of 30 data-plane requests succeeded, served from last applied state.
- A config write returned **503** in under a second with the message
  operators are promised: *"config writes need a quorum and this node
  cannot reach one; traffic keeps flowing from the last applied state."*
- `/admin/api/fleet` reported `quorum: false`, `live: 1`.

The first cut of this **hung** instead of failing — openraft's
`client_write` waits for a quorum that is never coming. Writes now check
quorum health up front and are bounded by a timeout, because an operator
editing config on a partitioned node has to be told, not left waiting.

## State reads during control-plane churn

A test hammers config writes through consensus while timing reads of the
applied state on another node. Reads stay flat: they touch a local
snapshot and never the log. Asserted in `chaos.rs` as a coupling check,
not a latency budget.

## What the tests found

Three real defects, all fixed, none of which unit tests would have caught:

1. **A node returning with the same id but an empty log panicked the
   leader.** openraft refuses follower log reversion — correctly, since a
   node that forgot its vote can break safety. In production a lost disk
   also loses `node.key`, so the box comes back with a *new* id; the join
   path now retires the stale member occupying that address. The chaos
   suite reproduced this only under sustained write load.
2. **Rate-limit shares counted membership, not liveness.** A dead box kept
   its share of every limit until an operator removed it. Members are now
   probed every 500 ms and counted live within a 1.5 s window.
3. **Writes to a follower were refused rather than forwarded**, breaking
   the promise that the console works the same on any node. Followers now
   forward to the leader and return what it committed.

## Storage correctness

The log store and state machine pass **openraft's own conformance
suite** (`Suite::test_all`) — the contracts consensus depends on (no
holes after truncate, purge semantics, vote durability, snapshot
round-trips) are checked by the algorithm's authors' tests rather than
ones we invented.

## Honest limits

- Cluster traffic is token-authenticated but **not TLS-encrypted**. Keep
  the cluster port on an internal network.
- `quorum` on a lone leader is inferred from `millis_since_quorum_ack`
  with a 2 s window, so there is a bounded interval after a partition in
  which a write is attempted before being refused.
- Budgets remain aggregation-based and lag by the flush interval, as
  documented since Phase 7. Clustering does not change that.
