# Phase 8 notes — replacing consensus with a store

Phase 8 was built twice. The first version put Raft in the binary and it
worked: three nodes, leader election, joint-consensus membership, 150
requests through a `kill -9` of the leader with zero failures. It was
then deleted, because the question "will this scale in ECS?" has a bad
answer for any design that gives a node a durable identity.

## Why the first version was wrong

Raft needs a node to be a pet. It needs stable identity, a disk whose
contents matter, and explicit membership changes on the way in and out.
An ECS service, an autoscaling group and a Kubernetes Deployment all
assume the opposite. Concretely, on ECS the Raft build would have:

* formed a new single-node cluster on every scale-out, because a task
  with no seed bootstraps rather than joins — silent, and it looks
  healthy;
* wedged below quorum on scale-in, because nothing calls `remove_voter`
  when ECS stops a task;
* re-replicated the whole state on every deploy, because Fargate storage
  dies with the task;
* and — the actual bug — failed to read any `store.*` secret on any node
  but the one that wrote it, because the data-encryption key was minted
  per node. Verified before rewriting: node B's unseal of node A's secret
  returned `None`.

The last of those was a real defect in shipped code, not a design
disagreement, and it is the one that convinced me the model was wrong
rather than merely awkward. A per-node key is only correct if nodes are
not interchangeable.

## What replaced it

One JSON document — config, virtual keys, sealed secrets, settings — plus
a version, in a backend that already knows how to be durable. Writes are
compare-and-swap on that version. Reads never leave the process.

| | Raft build | Store build |
|---|---|---|
| Node state that matters | WAL, snapshots, `node.key` | none |
| Node identity | stable u64, persisted | random per process |
| Joining | token, seed address, membership change | point it at the store |
| Leaving | `remove_voter` on the leader | stop it |
| Scale-in below half | cluster wedged | nothing happens |
| Config propagation | replication from leader | 3s poll |
| Ordering | replicated log | conditional write |

The trade is real and worth naming: config writes are no longer
linearizable across the fleet. They are compare-and-swap plus a
propagation delay. For a document a human edits, that is the right
trade — and it is what buys elastic, disposable nodes.

## Testing without AWS

The one contract everything rests on is that `commit` is atomic against a
concurrent writer. Testing that against a hand-rolled fake would only
prove the fake agrees with my assumptions, so the S3 and DynamoDB
backends are exercised through the real SDK against in-process servers
speaking the actual wire protocols — conditional PUT with
`If-Match`/`If-None-Match`, `PutItem` with a `ConditionExpression`.

The doubles are deliberately strict: the DynamoDB mock asserts on the
exact condition expression the backend emits and panics on any other,
and the S3 mock panics on any request it does not implement. A mock that
quietly accepted an expression it never evaluated would make the
compare-and-swap test pass without testing anything.

All four backends then run the *same* suite — round trip, concurrent
write, concurrent create, document fidelity, liveness — so a new backend
inherits the tests rather than needing its own.

## What the tests and the smoke run found

1. **The CLI's blocking commit helper was being called from inside the
   server's runtime** during first-boot bootstrap, panicking with
   "cannot start a runtime from within a runtime". Every unit test passed;
   only starting the actual binary caught it.
2. **A shared volume reintroduced the key bug.** The fallback key was
   written to the data dir, so two processes sharing a document but not a
   data dir would seal under different keys. The key now lives beside the
   document, so it follows the data rather than the node.
3. **A config that fails to build on one node must not take it down.**
   Mid-rollout, one task has a new secret and another does not. The node
   now declines the config, logs why, and keeps serving the last good one.
   The test for this was initially vacuous — it asserted a provider that
   was present in both the old and new config — and was rewritten to
   assert on something only the new config has.

## Two real binaries, one store

| Step | Result |
|---|---|
| Two nodes started against one document | both report `live=2, shares=2` |
| Config edited on A | B serving it 3s later, having never had it on disk |
| B stopped | A back to `live=1, shares=1` immediately |
| Cold node started, no config file, no data dir | serving the fleet's config, healthy |

## Honest limits

- **Rate limits are approximate.** Shares divide by a count that lags
  reality by up to the liveness window, and assume traffic is spread
  evenly. An exact global limit needs a shared counter on the request
  path, which the data plane deliberately does not pay for.
- **Store tuning is node-local** and must be set identically everywhere.
  A node cannot read the settings that tell it how to reach the document
  from the document. Mismatched windows across nodes make share counts
  oscillate, and nothing can detect that for you.
- **No namespacing** beyond bucket prefix or table name. Two environments
  pointed at one store will fight.
- **S3 `LastModified` has one-second granularity**, so liveness on the S3
  backend is accurate to about a second. Irrelevant at the default
  15-second window; worth knowing before tightening it.
