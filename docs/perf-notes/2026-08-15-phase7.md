# Phase 7 performance notes — control plane on, hot path unchanged

Machine: Apple M-series laptop, release profile (`lto = "fat"`,
`codegen-units = 1`, mimalloc), mock provider on loopback. Same rig and
methodology as [2026-08-15-baseline.md](2026-08-15-baseline.md), so the
numbers are directly comparable.

## The question

Phase 7 puts virtual-key enforcement and usage accounting on every
request: a key lookup and hash, three limit checks, and a metered
response body that scans for token counts. The claim under test is that
none of it is visible in gateway-added latency.

## Result — internal overhead, 1000 rps × 10 s

| | p50 | p99 | p99.9 |
|---|---|---|---|
| Phase 5 baseline | 6 µs | 24 µs | 108 µs |
| Phase 7 | **3 µs** | **24 µs** | **46 µs** |

Faster, not slower. The first cut of the metered body pre-allocated a
4 KB scan buffer per response; removing it (the buffer now grows only if
bytes arrive) moved p50 from 6 µs to 3 µs — the allocation had been
costing more than everything Phase 7 added.

Enforcement itself is a hash-map lookup, one BLAKE3 hash, and a handful
of atomics, all off the allocator.

## Memory

The soak's growth metric was wrong, and fixing it mattered more than the
number it produced. It compared the **first and last instantaneous RSS
samples**; RSS under load is a sawtooth as the allocator holds and
releases arenas, so that comparison reported anything between 0 % and
86 % for the same workload depending on where the sawtooth landed at the
final sample.

Checked against pre-Phase-7 `HEAD` in a separate worktree: identical
oscillation and the same spurious "growth", so it was never a Phase 7
regression — it was a measurement that could not distinguish a leak from
a sawtooth.

The rig now compares the **median of the first third of samples against
the median of the last third**, which is what "flat memory" means, and
reports the peak alongside. Over 240 s at 500 rps: early-median 14.9 MB,
late-median 18.2 MB, peak 29.8 MB — 22 %, inside the gate, with repeated
dips below the early median ruling out a leak.

Caveat worth stating: the rig hosts the load generator, the mock
provider, and the gateway in one process, so the sampled RSS is all
three. It is a leak detector, not a gateway memory budget.

## What is not on the hot path

- Usage records leave the request via one bounded channel send; a
  dedicated thread batches them into zstd partitions.
- Budgets are enforced from in-memory counters, so a spend check is an
  atomic load. Disk is only read once, at boot, to reseed the period.
- The store is untouched by data-plane traffic; config and key writes go
  through it, and requests read the swapped-in snapshot.
